# 代码结构

> 2026-09-18 结构重构后的模块地图与设计取舍。组织原则：**顶层按类型分区（Unity 惯例），Scripts 内按功能域分区（官方样例 Boss Room 同款做法），依赖方向由 asmdef 引用白名单在编译期强制**（对应 stick-world 的 `audit_deps.py` 零依赖环检查）。

## asmdef 依赖分层

```
                    ┌────────────┐
                    │ Editor     │（Editor-only 工具链）
                    └─────┬──────┘
                          ↓ 引用
        ┌─────────────────┼─────────────────┐
        │                 │                 │
  ┌─────┴─────┐     ┌─────┴─────┐     ┌─────┴────┐
  │ Pet       │     │ UI        │     │ Tests    │
  └─────┬─────┘     └─────┬─────┘     └─────┬────┘
        │    ┌────────────┘                │
        ↓    ↓                             ↓
  ┌──────────────┐              ┌──────────────┐
  │ Platform     │ → 引用 →     │ Core         │（零外部引用）
  └──────────────┘              └──────────────┘
        │
        └──→ Kirurobo.UniWindowController（UPM git 包，UniWinC）
```

规则：**高层可依赖低层，反向禁止**——想反向引用时编译期即失败（asmdef 白名单没给）。

## 设计取舍（为什么这样组织）

1. **应用式架构而非游戏式**：桌宠是常驻应用型程序（无"关卡"可编辑），主流做法是极少场景 + 代码组装 + 配置驱动，Prefab 工作流的核心收益（团队手工摆场景）在本品类不存在。因此**零 Prefab、SceneGenerator 代码生成全部版本场景**是有意选择（也承载"效果版本永久保留"约定：一版本一目录、成套重生成）。
2. **Pet 单程序集**：PetInputArbiter 与各物种控制器双向调用（TryClaim 下行 / CancelGrab 上行回调），按物种拆 asmdef 必成依赖环；物种边界用目录 + 命名空间表达，程序集边界到 Pet 为止。
3. **目录 = 命名空间**：asmdef rootNamespace 与目录对齐（`TransparentPet.Pet.Glass` 等），新增脚本落位即得正确命名空间。
4. **Core 与 Platform 分离**：原 Core 混装"事件总线/配置"与"Win32 互操作"两种职责；拆出 Platform 后，"Win32 互操作的谨慎区"（AGENTS.md 核心行为指令第 4 条）有了精确的物理边界。**唯一例外**：`Core/RoleEnvironment.cs` 持有 kernel32 Job Object 互操作（父死子亡配对）——它没有任何窗口 API、不影响透明/穿透行为，且调用方在 Core 的早期初始化链上，搬移到 Platform 会引入跨程序集初始化顺序风险，故经决策保留在 Core，并在文件头与 DllImport 处标注为 Core 的 Win32 例外。
5. **Assets 内零文档**：Unity 生态惯例——.md 会成为 TextAsset 出现在 Project 窗口；文档归仓库根 `docs/`（本文件即在此）。
